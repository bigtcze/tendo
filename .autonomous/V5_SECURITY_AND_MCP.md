# V5 identity, household authorization and MCP security contract

status=human_authorized

## Identity and household invariants
- User identity is global. Many-to-many `user <-> household` membership with a role per membership. Instance administrator is an independent, explicitly granted installation-wide capability; household administrator has no implicit cross-household authority.
- Current household must always be explicitly selected/validated on server; route IDs, SQL filters, search, subject references, completion history and counts MUST enforce household boundary regardless of frontend state. Stale sessions/roles and membership removal are tested.
- Preserve stable existing V4 user IDs, household IDs, OIDC immutable issuer/sub bindings, login credentials, tasks, persons/subjects and ledger entries. Safe migration policy for initial instance administrator: identify existing v4 owner/bootstrap authority using documented evidence, do not grant instance-wide rights to every household administrator by assumption. If unambiguous mapping is not possible, fail closed and provide a safe explicit CLI recovery/setup path.
- Last active instance admin and last admin within each household cannot be demoted, removed or deleted. Enforcement must be atomic under competing requests; UI disabled buttons alone do not count. Protect self-removal, cross-household delete, invitation acceptance and revoked members.
- User account deletion is an explicit confirmed destructive action, revokes sessions/OIDC/MCP credentials and removes or anonymizes personal fields while retaining required non-identifying household completion history/references. Document transaction and retention decisions; cover active items, ownership transfers, person links and multi-household members.
- Local-password change requires a LOCAL authenticated session and current password, CSRF/origin protection and rate limiting. OIDC-authenticated sessions cannot use this flow even if the account also has a local password. CLI administration reset is an interactive `tendo users set-password --login ...` design TARGET (the agent must implement and document actual command), no passwords in argv, `ps`, shell history or logs; restrict admin access through container/SSH. Session/token invalidation is mandatory.
- Cancelled/revoked invitations must not persist indefinitely as secret-bearing rows; remove active token and record optional minimal redacted audit. Expiry cleanup uses bounded retention and handles concurrent accept/revoke race. Migration safely purges existing cancelled/revoked rows while preserving history separate from invite tokens.

## MCP protocol
- Expose MCP over secure HTTPS deployment and Streamable HTTP. Validate the MCP protocol/authorization revision appropriate to supported clients, advertise Protected Resource Metadata and OAuth Authorization Server Metadata as required, issue OAuth codes with PKCE, use correct redirects/client registration strategy, audience-bound short-lived access tokens, refresh/rotation/revocation where provided and replay protection.
- Never accept an upstream OIDC ID token directly as a Tendo MCP bearer token without a verified authorization grant and correct audience. Existing OIDC may authenticate the human at the authorization step; the server must still implement a valid MCP OAuth authorization protocol. Use standard libs and robust threat model, not a speculative new identity framework.
- An MCP request resolves its own user identity/context and authorized household(s). No shared singleton user state, globally privileged API key, ambient cookie elevation, token forwarding to third parties or anonymous write endpoint. Safe for concurrent requests by two users.
- Effective permission = global MCP enabled AND per-user MCP enabled AND (administrator maximum scopes ∩ user-selected enabled scopes ∩ OAuth token scopes ∩ active household permission). User override only reduces. Both UI and MCP backend expose/verify per-user grants, with immediate revocation effect and auditable mutations.
- Tools should be small and useful: list households, list/search/detail items, create/edit, complete/undo, schedule/repeat, history, people/things as allowed. No instance admin tools, delete-user, permission self-elevation or arbitrary database access. MCP completion uses canonical tested application service and its idempotency/transaction semantics.
- Scope/audit records do not log raw credentials, full OAuth tokens or unnecessary household content. Rate limits, CSRF for browser flows, token audience/issuer, cross-household exfiltration and unauthorized tool calls have negative tests. Validate OAuth login locally with deterministic test IdP as well as protocol conformance. Protect disabled-MCP state at endpoint, not only in admin UI.

## Deployment considerations
- Keep only two required Compose services `app` and `postgres`. Do not regress V4 readiness, DB admin-bootstrap/runtime role segregation, production hardening or migration safety.
- Bind host IP defaults to 127.0.0.1; all-interface bind is explicit documented opt-in, never expose local app accidentally on upgrade. Verify secure proxy behavior, public origin and OIDC callback with variable host IP.
- Security design review required before schema/OAuth changes. Document trust boundaries, refusal cases and no-surprise migration from released v4.0.0.
