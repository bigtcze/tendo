## Objective
Ship a cohesive modern restyle across the existing Tendo application and address specific account-administration and identity UX defects. Do not turn Tendo into a developer tool, task tracker for GitHub, or enterprise portal. Preserve the existing v3 household workflows and security, use the existing React/Tailwind/Go/PostgreSQL architecture, and keep implementation modest, testable and maintainable.

## Explicit deliverables
1. Adopt the supplied cool, light, modern desktop and phone reference images. Design system: contemporary sans serif typography, off-white/blue-gray backgrounds, navy text, restrained deep teal/cyan action color, coral for attention, amber for waiting, subtle mint for upcoming. Define reusable tokens and deliberately designed dark/system variants. Redesign all existing routes and states, not just Home. Keep practical density and adaptive mobile/desktop behavior.
2. Add a genuine administrator-only **Admin center** integrated into existing navigation. Admin can see household accounts, change a member's role between **admin** and **member**, and initiate a secure self-service password reset for local-password accounts only. Protect on backend regardless of frontend visibility. Existing household owner becomes an admin; do not let the last active admin be removed/demoted. No global cross-household administrator. An existing owner retains administrator permissions on migration and current authorization checks must be remapped consistently, including invites. No notification settings UI or implementation in V4.
3. Make OIDC a working sign-in path even when the OIDC subject has no preexisting local Tendo account. On first successful OIDC login, create an account idempotently (even if no pre-existing Tendo account), bind it to immutable (issuer, subject), and give it a working signed-in state with a clear "join household by invitation" screen when not yet a member. **Verified matching email MUST automatically attach OIDC to an existing account instead of creating a second account**, but only when BOTH sides' email ownership is established and the match is unique; never infer ownership from display name or unverified strings.

**Verified repository baseline matters:** released v3 `user_accounts` has `login` but **no email column**, and the OIDC provider currently requests only `openid` and returns only `issuer/sub`. Therefore V4 must add a carefully migrated optional email + verification/provenance model, obtain `email` / `email_verified` claims (or validated userinfo with the identical `sub`) and establish a safe path for preexisting local users whose email was never recorded. Design and implement a practical one-time verification/admin-mediated resolution instead of silently duplicating accounts forever or falsely declaring all old accounts mergeable by email. Retain existing login/password accounts and sessions where appropriate. If email evidence is absent, unverified, duplicated or in conflict, DO NOT automatically attach the OIDC identity or merge household memberships; give an understandable and actionable recovery route. Existing OIDC-linked identities are authoritative by issuer/sub even if email changes. The goal is an effortless single-click normal case, not insecure identity takeover. OIDC login alone must not grant membership in a household; accept explicit invitations for household access. Do not assign admin from OIDC claims by default. Handle concurrent callbacks and changing email safely.
4. Remove existing manual SSO account-linking/pairing UI and flow from frontend; retain compatibility or remove legacy API as proven safe by audit. Existing linked identities continue signing in. Local password sign-in still works and existing accounts/data survive migration.
5. An existing registered household member **is already a person**. People and things must show/reuse the member as a person without requiring a second Tomáš/Anna person record. This must work structurally for task subject references, search/filter, selections, member rename/login changes and history — not merely render a decorative row. Keep optional explicit linking where useful for preexisting people records, but avoid duplicate identities and do not auto-merge solely by a matching name. Preserve tasks, history and household boundaries; migrate existing references idempotently.
6. Remove expired invitations from the frontend list and associated visible counters by default; leave API/DB audit history intact and preserve the ability to invite, accept and revoke active invitations.

7. Simplify the published Docker Compose deployment from three services (`postgres`, `migrate`, `app`) plus a root inline `configs:` block into **exactly two services: `postgres` and `app`**. Both PostgreSQL role bootstrap (currently the `postgres-init` config) and embedded SQL migration (currently `/tendo migrate` service) become **app startup responsibilities**, completing before HTTP listen/healthy/ready. Retain PostgreSQL data volume, existing restricted `tendo` runtime role, permission grants, schema migrations/locking/version/dirty checks and fail-closed behavior; validate fresh deployment and V3-to-V4 upgrade with real data. App uses a separate temporary privileged database connection at startup for role setup and migrations and the existing restricted connection for ordinary serving. Closing the privileged connection does NOT mean its credential is absent from the container environment: explicitly document and independently review this reduction in isolation versus the prior one-shot container. Do not add a new sidecar, bootstrap job, manual SQL step or separate required secret that negates the simplified install. Keep normal runtime hardening and update all Compose override, smoke, installation, upgrade, backup and release docs/tests accordingly. V4-16 owns the implementation, V4-13 is blocked until it passes.

## Security and migration boundaries
- Password resets: only admins, only users in the same household, only accounts with a local password. Generate single-use time-limited reset links/tokens stored hashed, shown only once; no email service required. Ensure CSRF/authorization checks, audit visibility, throttling, no cleartext credentials in logs; invalidate affected sessions/tokens as appropriate after reset. Do not expose raw password or let admin discover another user's password.
- OIDC provisioning must not allow account takeover via unverified/mutable email, issuer mismatch, or concurrency; identify by immutable issuer+subject after first login. Provider outage must not break local password login.
- Preserve v3 storage and accounts during upgrade, protected main/required CI, complete regression and contract tests. Update API and docs when behavior changes.
- For two-service Compose, **never** weaken the runtime DB role to superuser, mutate the existing named DB volume or start serving before role/schema initialization succeeds. If migration uses privileged DB credentials inside the long-lived app container, disclose that security tradeoff rather than presenting the deployment as equally isolated as v3.

## Explicitly out of scope
Notification configuration, delivery/channels, new integrations, AI, calendar synchronization, new project-management/productivity features, unrelated authentication methods, speculative architecture/framework rewrites, fake visual proofs, static images substituted for real application screenshots.
