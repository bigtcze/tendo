## Findings (as reported)


### V3-17-F1 — Home first-result keyboard path remains needlessly long
- Severity: should-fix-before-release
- Screen/evidence: Home 30-stage `home-30-en-390.png`, `home-30-en-1440.png`; `metrics.json` route measurements report 13 Tab stops to the first result at 320–1024 and 12 at 1440. Scripted journey J3 records 14 tab keypresses from page start.
- What is wrong: The daily use case is reaching a task that needs attention. Keyboard users must traverse skip/navigation, group overview links, and other chrome before the first actionable task. This materially weakens the “minimize taps / obvious next useful action” target. It is an improvement over baseline 14, but still a long path.
- Concrete fix: add a clearly named “Skip to needs attention” link/shortcut that targets the first actionable group/result, or reduce the number of focusable group overview links before results while retaining visible and accessible navigation. Ensure focus lands on a useful heading/result and is not hidden behind the fixed mobile nav. Likely sources: `frontend/src/features/items/HomeOverview.tsx`, `HomeGroupList.tsx` / `HomeGroupSection.tsx`, and shared shell navigation.

### V3-17-F2 — Home failure state still presents Add item as if the list were usable
- Severity: should-fix-before-release
- Screen/evidence: `audit-home-server-error-en-390.png`, `audit-home-server-error-cs-390.png`.
- What is wrong: A full-width primary Add item button remains under the error/retry notice while all household items are unavailable. The error is visible, but the action can imply this is a valid empty/partial home and encourage duplicate creation. This exact risk was called out in baseline finding B25 and remains.
- Concrete fix: suppress or demote Add item until the summary/list request is recovered; keep Retry as the single primary action for this state. If adding is intentionally allowed during an outage, explain that existing items could not be loaded and make the non-duplication risk explicit. Likely source: `frontend/src/features/items/HomeStates.tsx` / `HomeScreen.tsx`.

### V3-17-F3 — Long unbroken titles overwhelm the mobile detail hierarchy
- Severity: minor-later
- Screen/evidence: `audit-item-detail-long-title-cs-390.png` (also inspect corresponding long-title English capture if needed).
- What is wrong: An intentionally extreme long Czech title with long unbroken text wraps into a very tall serif headline and pushes status, actions, and detail below the fold. No horizontal overflow occurs, but the headline dominates the page and makes the primary action harder to find. The captured case is unusually adversarial; ordinary Czech names/diacritics fit.
- Concrete fix: keep word-breaking for safety but constrain headline measure/size at narrow viewports, and consider a slightly tighter display line-height for multi-line titles. Do not truncate the title or prevent access to actions. Likely source: `frontend/src/features/items/ItemDetailReadView.tsx` and shared heading styles in `frontend/src/index.css`.

### V3-17-F4 — Keyboard tab order is long across shared shell and dense results
- Severity: minor-later
- Screen/evidence: `home-30-en-390.png`; metrics J3 (`14` tab keypresses to first Needs attention row). All Items is a similarly dense query/result task.
- What is wrong: The fixed bottom navigation is visually clear and touch-friendly, but repeated navigation/overview controls add keyboard effort on the most frequent Home path (related to F1). Current captures show no target-size or horizontal-overflow violations.
- Concrete fix: prioritize an early skip-to-content/results mechanism and verify tab order/focus visibility at phone and desktop widths; avoid making essential content reachable only through pointer use. Likely source: shared navigation plus `HomeOverview.tsx`.

## Checked and found acceptable

- **Breadth:** inspected Home empty, 1, 30, 1200 at phone and wide breakpoints (including 768/1024/1440); add one-off and recurring fixed/after-completion forms in English/Czech; item detail, long notes/title, done/undo, archived, edit and 412 conflict; All items filters, page 2, no match, error and dark; People empty/populated; owner/non-owner Members; Account; login/error/dark; onboarding; invite accept/invalid; Home server error. Also sampled committed visual-regression snapshots across the available light/dark and 320/390/768/1440 matrix.
- **Width/layout:** authenticated desktop navigation rail and usable content width replace the old phone-column-in-empty-canvas composition. All Items uses a dedicated filter/results two-column layout at desktop; People/Members remain readable and uncluttered. Home is deliberately list-first rather than a dashboard. At 768px the phone-style navigation/content remain usable; mobile layouts retain full-width controls and wrap long metadata.
- **Density:** Home stages scale to large truthful counts with bounded, readable rows and a visible route to the full list. All Items exposes paged results and count; row density is more scan-friendly than the old stacked-card design. 1200-item Home samples retain a clear hierarchy; 1000+ search/filter/paging is available.
- **Forms and cadence:** one-off is the default simple path; repeat is progressive disclosure. Fixed and after-completion recurrence are separated and described with household examples (“boiler check”); Czech copy is natural enough and diacritics render. Controls/buttons are visually consistent, labels remain legible, and cancellation/save affordances are present.
- **States/actions:** detail exposes Done with reversible undo; done and archived states are visually distinct. Conflict preserves the user's form values and presents a recovery notice. Empty/no-match, permission, invalid-invite, and error states are differentiated; retry actions are apparent. Non-owner invitation screen says to ask a household owner.
- **Theme and rendering:** inspected light/dark Home, All Items, detail, add, login, People and Members samples. Palette remains warm and semantic in dark mode, without obvious low-contrast text, theme flash in these static captures, or broken icon/font glyphs/tofu. Icons are consistent, line-based and accompanied by text labels where important.
- **Localization/legibility/metrics:** Czech strings wrap in sampled routes; no clipping or horizontal overflow observed. `metrics.json` has 494 route captures: zero horizontal-overflow reports; smallest visible text is 14px; zero targets under 44px or under 24px. No “fluid”, “tenant”, “ETag”, or API jargon was noticed in sampled user-facing copy. The English login “Username” wording is understandable, though not especially household-warm.
- **Beginner journey records:** automated records exist for add one-off (2 steps/4 interactions), fixed+after-completion recurrence (3/15), needs-attention via keyboard, done/undo (2/2), search old done item (2/4), invite (2/2), and first-run (2/6). The recurring journey records the expected disclosure as an obstacle; the keyboard journey notes the 14 tab-key path; edit/archive/restore record carried a hard-coded note that Done is not available from detail. That note was stale and incorrect: item detail provides **Done** and **Undo** (`ItemDetailActions.tsx`), as the States/actions bullet above confirms. The note is removed from the audit harness (`frontend/e2e/audit/journeys.ts`) in the V3-17 docs PR. These are scripted counts, not observed novice performance.

## Limits

- This is an AI-only visual/UX review of provided screenshots, metrics, and locked design references. No human participants or household members were observed; no claim of human approval or user testing is made.
- Images are static; this review does not independently exercise keyboard behavior, zoom, screen readers, motion preferences, focus restoration, or runtime contrast. Metrics and journey records are supplied automation evidence, not a substitute for those checks or real-world use.
- Broad sample inspected, not every one of the 522 captures pixel by pixel. The review focused on the requested routes/states and representative viewport/locale/theme combinations.
