# V3 accessibility review

> Historical record. It describes the V3 stage (released as `v3.0.0`) and is not the current UX or security contract. Current contracts: [UX](../../.autonomous/UX.md), [SECURITY](../../.autonomous/SECURITY.md).

## Automated evidence

The production-browser E2E suite runs axe scans (WCAG 2.2 A/AA tags), measured text and control-boundary contrast, keyboard focus sweeps, target-size checks, responsive widths and zoom coverage. The route and measured-state scans run with both the real stored Light/System preference and the persisted Dark preference; tests assert `html[data-theme="dark"]` before accepting dark-mode results. Firefox and WebKit run a bounded owner journey across the primary household routes and widths.

These are automated WCAG-oriented checks, not a certification or a substitute for human testing. The existing release-qualification Orca harness remains the assistive-technology qualification layer; no human screen-reader test is claimed here (G12 limitation). Manual-style checks of landmarks, labels, live regions, touch comfort and long-string wrapping require human review and are not claimed complete by an axe pass.

## Findings and fixes

Automated Chromium accessibility evidence: n21 emits zero measured non-exempt contrast shortfalls and zero focus-ring shortfalls across audited light/dark routes and states; axe WCAG scans pass. Covered dark snapshots include All items no-results and Home 500 error, plus Repeat-on Add form, item edit form and undone history. The empty-state audit is unconditional: it asserts the search field, no-match result, axe scan, full keyboard reach-equality and target-size compliance using the same label-hit-area predicate as other route checks.

The dialog keyboard sweep now measures unfocused indicators before Tab begins and does not blur/refocus controls between Tab presses. A focused/unfocused date-input probe confirmed that blur/refocus resets native date segments and can keep Tab on the same input indefinitely (30+ presses in Chromium, Firefox and WebKit); without blur/refocus the date input leaves after the expected segment presses. Only a native `input[type="date"]` may keep focus across consecutive Tab presses, for at most 3 additional presses after first arrival (the longest observed engine behaviour; `frontend/e2e/tabRepeatGuard.ts`). Any other element that keeps focus on Tab fails immediately as a trap, and non-consecutive repeats remain loop failures. `primitives-browser.spec.ts` self-tests the guard with real Tab presses (a Tab-swallowing button traps; a native date input passes) and checks that it fails when the non-date rule is removed. Modal checks require every visible enabled dialog control exactly once per cycle, focus containment in `<dialog open>`, visible changed focus, unobscured targets and focus-ring contrast >=3:1. Modal loop/footer checks do not apply because the modal is expected to cycle and has no page footer.

Invitation theme proof: the invite route captures its token and removes the fragment using `history.replaceState`, so a subsequent `/invite#token` navigation can be hash-only and does not rerun `theme-boot.js`. The test records a window marker and unchanged navigation-entry count across that same-document navigation, then uses a fresh document navigation through `about:blank` with the stored dark preference. The fresh token URL renders the invitation with dark theme; this is not a product bug.

Cross-browser focus: on each route, width and theme, Firefox and WebKit identify the first Tab target in DOM order and record its unfocused outline/shadow. They then press Tab and require that the same element is focused, that it paints a visible outline or non-transparent shadow (`frontend/e2e/focusIndicator.ts`), and that its indicator differs from the unfocused one. Measurements wait until route loading statuses and `aria-busy` regions are gone. A primitives self-test confirms the painted check rejects `outline:none; box-shadow:none` and fails if the helper is stubbed to true.

Cross-browser search: Firefox and WebKit each search for the newly created uniquely titled item using both the Search button and Enter, and assert the result link is visible. The earlier Firefox miss has not been causally reproduced, so no root cause is claimed. The current test first verifies the uniquely titled item is persisted through the API, then runs and asserts both user-facing search submit paths in Firefox and WebKit. Both paths pass in the full suite; no product defect or Vitest regression is indicated by this reproduction.

## Manual-style source and screenshot review

An independent source/screenshot review (no assistive technology run) checked labels, descriptions, live regions, dialogs and confirmation context. Confirmed defects were fixed with Vitest regressions that fail on the previous code:

| Finding | Fix | Regression |
|---|---|---|
| Item date and "Last completed on" fields lost their hint description whenever they were not the invalid field: the form's invalid-field props overwrote the `Field` hint id with `undefined`. | Hint ids are always kept; the form error id is appended only to the invalid field. | `ItemForm.test.tsx` "keeps date hints described while valid…" |
| The fixed/after-completion example sentence was not associated with the "Count the next repeat from when I complete this" switch. | The switch is described by the example, which updates with the toggle. | `ItemForm.test.tsx` "describes the count-from-completion switch…" |
| The inline "Revoke? Yes" confirmation gave no context about the invitation it applies to. | "Yes" is described by the question and that row's created/expires line. Dates are day-only, so two invitations created the same day still share a description; the confirmation stays inside its own list row. | `MembersScreen.test.tsx` revoke confirmation flow |

Reviewed and not changed: dialog dismiss buttons are labelled "Cancel" (visible text equals accessible name, and dismissing discards the draft as cancel implies); login and invitation field errors already use `role="alert"`, while non-field outcome notices are focused `status` regions; the header truncates a long signed-in name visually but exposes the full text, and the Account page shows it unwrapped with `break-words`.

The initial Firefox and WebKit smoke invocations exposed test-fixture race/selector assumptions; the cross-browser flow verifies the created resource by stable API ID for detail and waits for the persisted undo response. Final validation on the same tree: `npm run check` passed (lint, typecheck, 900 Vitest tests, build); two consecutive complete `bash scripts/e2e-smoke.sh` runs passed in 362s and 363s. Each run included 62 e2e tests, one Firefox and one WebKit cross-browser project, and both clock phases, with zero failures, retries, flaky tests, or skips. Axe `incomplete` contrast checks where pseudo-element or overlay backgrounds cannot be resolved remain attached for review and are not suppressed. Automated checks are not certification or a substitute for human testing; the G12/no-human-screen-reader limitation remains.
