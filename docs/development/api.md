# API conventions

The contract is `api/openapi.yaml` (OpenAPI 3.1). It is edited together with the code that implements it. The locked policy is `.autonomous/API.md`; this page describes what is implemented.

## Basics

- Base path `/api/v1`. JSON field and query parameter names are `camelCase`; timestamps are RFC 3339 UTC.
- Authentication is the session cookie. State-changing requests also need the canonical `Origin` header (missing or foreign origin returns `403`).
- Household resources live under `/api/v1/households/{householdId}/...`. The household ID is checked against membership on every request.
- Responses carry `X-Request-ID` and `Cache-Control: no-store`.

## Errors

Errors use `application/problem+json` with `type`, `title`, `status`, and a stable `code`. Clients must not parse `detail`.

| Status | `code` | Meaning |
| --- | --- | --- |
| 400 | `invalid_request` | Malformed JSON, unknown, duplicate or null keys, wrong value types, empty patch |
| 400 | `invalid_query` | Bad query parameter; `parameter` names `limit`, `cursor`, `archived`, `done`, `subjectId`, `responsibleUserId`, `workflowState`, `attention`, `recurring`, `sort`, `attentionDate`, `q`, `id` (subject list), `order` (completion history), or `includeExpired` (invitation list) |
| 401 | `unauthenticated` | No valid session |
| 404 | `not_found` | Malformed ID, nonexistent resource, resource of another household, or caller not a member. The bodies are identical |
| 404 | `invalid_invitation` | Malformed, unknown, expired, revoked, or already-used invitation token |
| 404 | `invalid_password_reset` | Malformed, unknown, expired, revoked, already-used, or no longer authorized password reset token |
| 403 | `owner_required` | Legacy code on invitation routes: caller is a current household member but not an admin managing invitations |
| 403 | `admin_required` | Caller is a current household member but not an admin managing accounts |
| 400 | `idempotency_key_required`, `invalid_idempotency_key` | `Idempotency-Key` is missing or malformed on invitation, subject, item, or completion create |
| 409 | `already_member`, `household_conflict` | Existing-account invitation acceptance conflicts with current membership/default household |
| 409 | `cannot_reset_self`, `no_local_password` | An admin targeted their own account, or the target signs in only through OIDC |
| 409 | `member_person_locked`, `member_person_exists`, `member_person_changed` | A member's canonical person cannot be unlinked/relinked/retyped/archived by PATCH; a member already has a person; or a transfer's current person changed |
| 429 | `rate_limited` | Session, invitation acceptance, password-reset issuance (per client address and per target account), or password-reset redemption limit; response includes `Retry-After` |
| 412 | `precondition_failed` | `If-Match` is malformed, weak, a list, or stale |
| 413 | `content_too_large` | Body over the limit (4 KiB for subjects; 64 KiB for items) |
| 415 | `unsupported_media_type` | Body is not `application/json` |
| 422 | `invalid_length`, `invalid_characters`, `invalid_type` | Validation failure; `field` names the property. Subject names are 1 to 100 characters after trimming and may not contain control, format (zero-width, bidirectional) or line and paragraph separator characters |
| 428 | `precondition_required` | `If-Match` missing on `PATCH` |
| 503 | `unavailable` | Persistence failure; no internals are exposed |

## Invitations and members

- Household roles are `admin` and `member`; the `MemberRole` enum no longer contains `owner`. There is no global admin, and the role is never derived from OIDC claims or email. Only a current household admin may create, list, or revoke invitations. Members receive the legacy `403 owner_required` on these three routes; the account routes below return `403 admin_required`. Non-members and unknown households receive uniform `404 not_found`. `defaultHouseholdId` grants no access.
- Create with `POST /api/v1/households/{householdId}/invitations` and one visible-ASCII `Idempotency-Key`. The body is exactly `{}`. A first creation returns `201` and the raw bearer token once; same-key retry returns `200` without it. Both responses include `Location`. Missing key returns `400 idempotency_key_required`; invalid or duplicate keys return `400 invalid_idempotency_key`. Tokens are never included in list responses.
- Admin list uses `limit` and opaque `n1:` cursors. Members list uses opaque `m1:` cursors and is available to any household member. Both default to 50 and cap at 100. The admin invitation list also accepts `includeExpired` (`true` by default for compatibility; exactly one lowercase `true` or `false`, else `400 invalid_query` naming `includeExpired`). With `false`, never-accepted, never-revoked invitations whose `expiresAt` is at or before the request instant are filtered in the query before the page limit, so pages and `nextCursor` reflect only the remaining rows; the web app always sends `false`. Filtered rows stay stored and unredeemable. A cursor names only the last returned ID, so it may be reused with either value.
- Revoke succeeds for terminal invitations and does not remove members. New-account acceptance is `POST /api/v1/auth/invitations/accept`, returns `{userId, login, householdId, role}`, and does not set a session cookie; sign in through `POST /api/v1/session`. Existing-account acceptance is `POST /api/v1/invitations/accept`, returns `{userId, householdId, role}`, and rejects an account with an existing default household or other household membership (`409 household_conflict`); an existing member gets `409 already_member`. Malformed, unknown, expired, revoked, and already-used tokens all return `404 invalid_invitation`.
- Request evaluation order for management routes: global Origin/authority middleware (400 for malformed trusted forwarded metadata, 403 Origin, 421 authority) → session authentication (401, clearing a stale single cookie) → Idempotency-Key syntax (create only) → strict body decode → service authorization/not-found. Thus forbidden Origins are rejected before session lookup; authenticated members with malformed body/key see syntax errors before admin authorization. All responses include `X-Request-ID`; application responses use `Cache-Control: no-store`.
- Admins manage accounts with `GET .../accounts` (cursor paged, limit at most 100), `GET .../accounts/{userId}` (strong `ETag` equal to the membership version), and `PATCH .../accounts/{userId}` with `{"role": "admin" | "member"}`. PATCH requires `If-Match`; missing returns `428`, malformed, weak, listed or stale returns `412`. An unchanged role is a no-op with no version bump and no audit row. A change that would leave zero admins returns `409 last_admin`; self-demotion succeeds while another admin remains. Accounts expose `signInMethods` `{password, oidc}` booleans, a nullable `passwordReset` `{createdAt, expiresAt}` fact (only when a usable link exists), and never credentials. See `api/openapi.yaml` for the exact schemas and responses.
- Admins issue a local-password reset link with `POST /api/v1/households/{householdId}/accounts/{userId}/password-reset` and an empty body. The target must be a member with a local password (local-only or local+OIDC); OIDC-only returns `409 no_local_password`, and the admin cannot target themselves (`409 cannot_reset_self`). A first issue returns `201 {token, createdAt, expiresAt}` with `Cache-Control: no-store`; only the SHA-256 digest is stored. Issuing again revokes the previous outstanding link in the same transaction, and the partial unique index guarantees at most one usable link per account. `DELETE` on the same path revokes the outstanding link and is idempotent (`204` even when none exists). Both routes evaluate in this order: global Origin/authority middleware (400/403/421) → session (401) → rate limiters → strict body (issue only) → service authorization (`403 admin_required`, `404`, `409`). Forbidden origins and unauthenticated callers are therefore rejected before any bucket is consumed; a malformed body is rejected after the limiter has counted the attempt. Issuance is limited per client address (10 per minute) and, independently, per target account (5 per hour); the second bucket is keyed by `userId` and applies to issuance only, so cancelling is never target-throttled. Both answer `429 rate_limited` with `Retry-After`, and the client shows one calm "too many links" message. The full rationale is [ADR 0014](../adr/0014-admin-password-reset.md).
- Redeem with public `POST /api/v1/auth/password-reset` `{token, password}`. It requires the canonical Origin, is limited to five attempts per client IP per minute, and answers `200 {login}` so the client can prefill sign-in. The password follows the same 15-128 character policy (`422 invalid_length` on `password`) and is hashed outside the transaction. The token row is locked `FOR UPDATE`; the target must still be a member with a local credential and the issuer must still be an admin of the same household, otherwise the link is void. The target's credential row is then locked `FOR UPDATE` before the write, and the update increments `credential_version`; an update that affects no row aborts the whole transaction as `404 invalid_password_reset` without consuming the link. Sign-in re-reads hash and version under `FOR SHARE` in the transaction that inserts the session, so a login racing a reset either commits first and has its session deleted or fails as a wrong password (see [ADR 0014](../adr/0014-admin-password-reset.md)). Success replaces the password, marks the link used, and deletes every session of the target. Malformed, unknown, used, revoked, expired, or no-longer-authorized links all return the same `404 invalid_password_reset`. Tokens and passwords are never logged or stored in cleartext.
- `GET /api/v1/households/{householdId}` returns `viewerRole` (`admin` or `member`) for the caller, read in the same authorization query. It is a presentation hint for the admin-only Admin center entry and grants nothing: every account route re-authorizes the caller, so a member who opens the screen sees only the calm `403 admin_required` state. The field is additive and marked required in the response schema because every server version that ships it always sets it and the web client is embedded in the same binary; older clients ignore unknown fields. The hint can go stale when another admin changes the caller's role; the client refreshes it whenever an account route answers `403 admin_required`. The account `ETag` is the membership version and covers role changes only: it does not cover `passwordReset`, which is a separate no-store identity fact read in the same response, so a client must not cache or revalidate an account representation to decide whether a reset link is still outstanding.

## Subjects

- `linkedUserId` is always present in subject representations and is either a member `userId` or `null`. It is the canonical member-person link: every household membership has exactly one linked `person` subject, provisioned in the same transaction as the membership (setup and invitation acceptance), and the link is unique per `(linkedUserId, householdId)` by a partial unique index. The association remains descriptive only and grants no access. Non-null UUIDs are canonicalized to lowercase. Invalid, malformed, or foreign-household references return `422 invalid_reference`; a non-person linked result returns `422 requires_person`; membership lookup outages return `503 unavailable`.
- A member person is locked: PATCH cannot unlink or relink it, change its type away from `person`, or set `archived: true` (`409 member_person_locked`). Same-value no-ops, `archived: false`, and name edits are allowed. Create with a valid member `linkedUserId` returns `409 member_person_exists`, and PATCH linking an unlinked subject to a valid member returns the same, because that member already has a person. Invalid references still take precedence. Replay lookup runs before the create conflict check, so earlier idempotent creates keep replaying.
- Read the canonical person for a member with `GET /api/v1/households/{householdId}/members/{userId}/person`. Any household member may read it; the response is the member's linked `Subject` with the strong subject-version `ETag`, so a client can build a transfer without paging the subject list. Malformed, foreign-household, non-member, and unlinked user identifiers all return the same `404 not_found`.
- Reassociate an existing unlinked person explicitly with `PUT /api/v1/households/{householdId}/members/{userId}/person` and `{subjectId, subjectVersion, currentSubjectId, currentSubjectVersion}`. Any household member may call it. One transaction locks the membership and both subjects, verifies that `currentSubjectId` is exactly the member's linked person (`409 member_person_changed` otherwise) and that both versions match (`412 precondition_failed`), then unlinks the current person and links the target. The response is `200 {person, personVersion, previous, previousVersion}`; both versions are bumped, the previous person stays active and unlinked, and no item or history row changes. The explicit versions match what a subsequent GET exposes as the strong ETag. An archived, non-person, already-linked, or same target returns `422 not_eligible` on `subjectId`; malformed or cross-household identifiers return `404 not_found`.
- For create idempotency, the lowercase linked UUID is appended to the intent fingerprint only when non-null; omitted and explicit null retain the original v1 fingerprint and replay equivalently. Key lookup remains before linked-reference validation, so replay after later link edits returns the current subject representation without rechecking the link. A different link using the same key returns `422 idempotency_key_reused`.
- Create with `POST /api/v1/households/{householdId}/subjects` and exactly one case-sensitive `Idempotency-Key`: 1–128 visible ASCII bytes (`0x21`–`0x7E`). Missing returns `400 idempotency_key_required`; empty, invalid, or repeated headers return `400 invalid_idempotency_key`. Evaluation order: global Origin/authority middleware (400/403/421) → session (401) → key syntax (400) → strict body decoding (415/413/400) → household membership (404) → replay lookup → name/type validation (422).
- Keys are scoped to the resource kind, household, authenticated actor, and key. Membership authorization is still required on every retry. Replay lookup occurs after membership and before name/type domain validation. The intent is the trimmed name and the exact type. A matching submitted intent returns `201` with the subject's current representation, ETag, and original Location; edits and archive state made since creation are reflected and no version is incremented. Reusing a key for a different intent returns `422 idempotency_key_reused` without a `field`. Invalid or rejected requests do not reserve a key.

## Items

- Create with `POST /api/v1/households/{householdId}/items` and exactly one case-sensitive `Idempotency-Key`: 1–128 visible ASCII bytes. Missing returns `400 idempotency_key_required`; empty, invalid, or repeated headers return `400 invalid_idempotency_key`. Evaluation order: Origin/authority → session → key syntax → strict body decode → household membership → replay lookup → domain validation.
- Keys are scoped by resource kind, household, authenticated actor, and key. Replay identity uses the decoded creation intent (including explicit null versus empty, canonical UUIDs and canonical recurrence). A matching retry returns `201` with current item representation/ETag and original Location; changed intent returns `422 idempotency_key_reused` without a field. Replay happens before validation, so later subject archival does not prevent it. Historical initialization creates one receipt only for the committed creation; replay after receipt undo does not create another.

## OIDC authentication

- `GET /api/v1/auth/oidc` reports whether the configured provider is enabled; `displayName` appears only when enabled. `GET /api/v1/auth/oidc/identity` requires a session and reports `{linked}`.
- Start with `POST /api/v1/auth/oidc/start` and `{ "purpose": "login" }`, or link with `{ "purpose": "link", "currentPassword": "..." }` while signed in. Linking reauthenticates the local password. The request requires canonical Origin; success returns an authorization URL and sets a ten-minute HttpOnly flow cookie.
- Login start may carry `invitationToken`; it must reference a pending invitation (else `422 invalid_invitation`) and only its hash is stored with the flow.
- The provider callback is `GET /api/v1/auth/oidc/callback`. It consumes the single-use flow and always returns an empty `303` redirect to a fixed application route. Success sets a fresh session cookie; link success revokes the initiating session. Failures expose only stable `oidcError` codes. First-login routing follows [ADR 0012](../adr/0012-oidc-jit-and-verified-email.md): signed in (`/`, or `/#oidcNotice=invitation_accepted|invitation_invalid` with a carried invitation), `identity_conflict`, or `/login#oidc=continue` with a ten-minute HttpOnly pending cookie. `identity_not_linked` is no longer emitted.
- Pending continuation routes require canonical Origin for writes, share the sign-in throttle, and return `409 already_signed_in` while a session cookie is valid: `GET .../oidc/pending` (status, no email echoed, `404 pending_not_found` when unusable), `POST .../oidc/pending/account` (new account, `201` session plus `invitation` outcome), `POST .../oidc/pending/link` with `{login, password}` (`401 invalid_credentials` for any wrong pair, five failures end the continuation; `201` with `invitation` and `emailSaved`), and `DELETE .../oidc/pending` (`204`, idempotent). `POST .../oidc/account/discard` (session) deletes an account without membership, password or other identity and returns a fresh continuation, else `409 account_not_discardable`.

## Cursor pagination

Collections return `{"items": [...], "nextCursor": string | null}`. `nextCursor` is always present and is `null` on the last page.

- `limit`: integer 1 to 100, default 50.
- `cursor`: the `nextCursor` of the previous page. It is opaque and versioned; do not build or parse it.
- Items default to `sort=created`, ordered by `id` ascending (UUIDv7, so creation order). `sort=attention_on` orders by `attentionOn` ascending, null first, then ID ascending; null means the item needs attention now. Sort accepts exactly one nonempty `created` or `attention_on` value. A keyset traversal guarantees unchanged rows keep their order and are not duplicated; concurrent edits to sort keys may move rows across the boundary.
- Invalid values return `400 invalid_query`. Unknown query parameters are ignored.
- Subjects: `archived=false` (default) lists active subjects; `archived=true` lists archived ones only. Repeated `id` query parameters (for example `?id=<uuid>&id=<uuid>`) filter to at most 100 supplied canonical UUID values (8-4-4-4-12; case-insensitive); duplicates are canonicalized and removed. Empty, malformed, or more than 100 values return `400 invalid_query` with `parameter: id`. Filtered pagination cursors bind the household, archived partition, and canonical sorted ID set; changing any filter invalidates the cursor. `s1:` cursors remain the unfiltered format and cannot be mixed with `id`; filtered `s2:` cursors cannot be used without it. Query evaluation order for this route: Origin/authority middleware → session authentication (401) → transport query checks (`limit` syntax and 1–100 range, `cursor` nonempty single value, `archived` syntax, then `id` values nonempty with at most 100 supplied) → household membership authorization (uniform 404) → semantic UUID validation and cursor decoding/binding (400). Thus malformed UUID syntax is concealed by the uniform 404 for non-members, while malformed UUIDs for a member return `400 invalid_query` with `parameter: id`.
- Items: `archived=false` (default) lists active items; `archived=true` lists archived items only.

## Evaluation order

Checks run in this order and the first failure is returned: 403/421 origin and authority (global middleware), 401 session, 428/412 `If-Match` syntax, 415/413/400 request body, 404 household membership and target existence, 422 field and reference validation, 409 member-person conflicts, 412 stale version. For subject PATCH the service reads the household-scoped target before field validation, preserving 404-before-422; a lookup outage returns 503 unavailable. Item PATCH uses an equivalent household-scoped target lookup when field/reference validation would fail first. For subject PATCH the stored row is also the basis for semantic validation: an unlinked non-person linked by the patch returns 422 `requires_person`, an unlinked person linked by the patch returns 409 `member_person_exists`, and an existing member person that the patch would unlink, relink, retype away from `person`, or archive returns 409 `member_person_locked`. These 422/409 results are evaluated against the current stored state and take precedence over staleness. Only a semantically valid patch on a row whose version differs from `If-Match` returns 412, and the service never runs the UPDATE in that case; the version-guarded UPDATE also prevents a concurrent change from applying an invariant evaluated against an older state. Completion undo is an exception to the generic existence-before-validation ordering: `undone` body validation occurs before membership and item/receipt lookup, as documented in `api/openapi.yaml`. The `PATCH` consequence: a non-member who omits `If-Match` gets 428, and one who sends a well-formed `If-Match` gets the uniform 404. `If-Match: *`, weak tags and lists are rejected with 412.

## Items

- Create and update accept a title of 1 to 200 Unicode characters after trimming; the stored title is trimmed. Notes, when present, contain 1 to 4,000 Unicode characters and are stored exactly as provided. Send `notes: null` to clear notes. Control, format, and line/paragraph separator characters are rejected in titles; notes also reject those characters except newline, carriage return, and tab.
- `subjectId` must identify an active subject in the same household. Invalid, archived, or foreign-household subjects return `422 invalid_reference` for `subjectId`.
- `responsibleUserId` is always present in item representations and is either a user UUID or `null`. On create, omit it or send `null` to leave the item unassigned; a string assigns it. On PATCH, omission preserves the assignment, `null` clears it, and a string assigns/replaces it. The candidate must be a member of the item's household in any role; any household member may assign any other member, and the ID matches `userId` in the members list. Malformed, unknown, or foreign-household IDs return `422 invalid_reference` on `responsibleUserId`; a subject-reference error takes precedence. A membership lookup outage returns `503 unavailable`.
- Completion and undo do not snapshot or restore the responsible member: they preserve the item's current assignment, including changes made after completion. The database uses a restrictive membership FK, so future member-removal flows must explicitly clear responsible assignments with normal item version bumps before deleting memberships.
- `attentionOn` is an optional date-only value. On creation, without it, the item is `needs_attention` immediately unless `historicalCompletedOn` supplies the first attention date; before the date it is `upcoming`; on or after the date it is `needs_attention`. On PATCH, omitted leaves the stored date unchanged; `null` clears it, making the item need attention immediately. The derived `attention` is evaluated per request using the household timezone and is not stored.
- Item responses use `Cache-Control: no-store`. The strong ETag identifies the stored item version used for `If-Match`; the derived `attention` value can change at household-local midnight without changing that version.
- `workflowState` is one of `open`, `in_progress`, `waiting`, or `paused`. Archive and unarchive with the `archived` boolean; archived items remain directly readable and editable.
- `recurrence` is null for Repeat OFF (one-off). On create, omitted or null means one-off. On PATCH, omitted leaves the policy unchanged, null turns Repeat off, and an object replaces the whole policy. A policy contains an integer interval value (1–999), unit (`day`, `week`, `month`, `year`), and mode. Non-integer JSON values, including fractions and exponent notation, are `400 invalid_request`; integer literals beyond signed 64-bit range are clamped for validation and return `422 invalid_interval`. Repeat and Fluid are distinct choices: `fixed` means Repeat ON / Fluid OFF; `after_completion` means Repeat ON / Fluid ON. The policy determines the next cycle when the item is completed. Setting, changing, or clearing recurrence does not reschedule `attentionOn`, except explicit historical initialization; `attention` remains derived from `attentionOn` and household-local today.
- On create only, optional non-null `historicalCompletedOn` is a real `YYYY-MM-DD` known date; explicit null is `400 invalid_request`, while omission means absent. It requires enabled recurrence, conflicts with non-null `attentionOn`, and cannot be after household-local today (today is allowed). It creates an explicit completion receipt by the authenticated actor and initializes `attentionOn` as that date plus the recurrence interval for both modes. It never uses today as the historical date. The creation Idempotency-Key reserves this intent and prevents duplicate item/receipt creation on retry. The initial creation returns version 2 / ETag `"2"`; without historical initialization it returns version 1 / ETag `"1"`. A same-key replay returns the current item representation and ETag, which may reflect a later version. A computed attention date already in the past stays past. Create validation order after auth/household checks: title, notes, recurrence, attentionOn, historical date syntax/calendar, recurrence requirement, attentionOn conflict, future date, computed date overflow, then subject reference. Validation returns 422 `invalid_date`, `requires_recurrence`, `conflicting_fields`, or `future_date` on `historicalCompletedOn`; arithmetic overflow returns `date_overflow` on `recurrence`. The field is not accepted on PATCH.
- Invalid recurrence values return 422 with `field: recurrence` and `invalid_interval`, `invalid_interval_unit`, or `invalid_mode`.
- List accepts `limit` (1–100, default 50), opaque `cursor`, `archived` and `done` (`true` or `false`; both default `false`), `sort` (`created` by default or `attention_on`), optional `attentionDate`, plus `subjectId` (UUID), `responsibleUserId` (UUID or exact `unassigned`), `workflowState` (`open`, `in_progress`, `waiting`, `paused`), `attention` (`needs_attention`, `upcoming`), and `recurring` (exact lowercase `true` or `false`). Each optional value is single-valued; filters combine with AND. Empty/repeated/comma-list values and invalid values return `400 invalid_query` naming the parameter. UUIDs are case-insensitive; well-formed unknown/foreign IDs return an empty list, and archived subjects are valid filter targets. Filter matches are applied before the page limit.
- `q` is an optional single-valued literal contiguous substring wholly within a title or notes. A present-empty or repeated `q` is a structural `400 invalid_query` (`parameter: q`) before household membership; whitespace-only, forbidden control/format/line/paragraph separators, or more than 200 Unicode code points after trimming is a semantic `400` after membership. Thus a non-member with semantically invalid `q` gets the uniform `404` first. Case folding uses PostgreSQL 18 Unicode casefolding; NFC normalization and unaccent make Czech diacritics match unaccented text for NFC/NFD input. `%`, `_`, `\\`, and commas are literal search text (commas do not form a list); a query normalizing to empty matches nothing. It is ANDed with all filters before pagination/counting.
- `attentionDate` must be exactly one canonical, real `YYYY-MM-DD` date and match household-local today. It is a freshness guard only, never an as-of date. A mismatch returns `400 invalid_query` with `parameter: attentionDate`; clients should restart the list from page one after local midnight.
- Cursor selection/bindings: omitted or explicit `sort=created` with V1-only query parameters keeps the V1 cursor format unchanged. Any structured filter, `sort=attention_on`, a supplied `attentionDate`, or nonempty `q` uses an extended cursor bound to the household and the normalized query (filters, archived/done, sort, guard presence). Changing filters, sort, or guard presence invalidates continuation with `400 invalid_query`, normally naming `cursor`; changing `q` (including case or accent changes) also invalidates continuation because the trimmed exact query text is bound; a malformed or stale supplied guard names `attentionDate` before cursor validation. Changing `limit` is allowed. Cursors from requests with an attention filter or guard expire at household-local midnight; attention-sort-only cursors do not. Traversal is deterministic for unchanged matching rows; it is not a snapshot, so a row whose sort key or matching state changes between pages may move across the page boundary. Cursors are opaque and unsigned; unknown query parameters remain ignored.

### Item summary

`GET /api/v1/households/{householdId}/items/summary` returns the counts for the complete matching collection, without pagination. It accepts the same filters and semantics as item listing: `subjectId`, `responsibleUserId` (including `unassigned`), `workflowState`, `attention`, `recurring`, `q`, and the `attentionDate` household-local-today freshness guard. Presence of `limit`, `cursor`, `archived`, `done`, or `sort` is rejected with `400 invalid_query` naming that parameter.

The response fields are `evaluatedOn`, `total`, `needsAttention`, `inProgress`, `waiting`, `upcoming`, `paused`, `done`, and `archived`. Each item belongs to exactly one partition, in precedence order:

| Precedence | Partition | Rule |
| --- | --- | --- |
| 1 | `archived` | Archived item |
| 2 | `done` | Completed one-off item |
| 3 | `paused` | Workflow state paused |
| 4 | `inProgress` | Workflow state in_progress |
| 5 | `waiting` | Workflow state waiting |
| 6 | `needsAttention` | Open item with no attention date or date ≤ today |
| 7 | `upcoming` | Open item with attention date > today |

`total` equals the sum of the seven counters; an empty result has all counters zero. `evaluatedOn` is household-local today and can be supplied as `attentionDate` to reject a stale response after midnight. Summary responses have no ETag. Summary and list requests are not snapshot-bound to one another.

## Completions

- Create a receipt with `POST /api/v1/households/{householdId}/items/{itemId}/completions`. `Idempotency-Key` is required, case-sensitive, 1–128 visible ASCII bytes with no normalization. `If-Match` must contain the current strong item ETag. The body may be `{}` (household-local today) or specify `completedOn` as a valid, non-future business date.
- Evaluation order is session/origin, If-Match presence/syntax, idempotency header, media/body validation, household membership/item existence, then idempotency lookup under the item lock before future-date, version, lifecycle, and recurrence-overflow checks. The fingerprint binds actor and submitted-date presence/value; it excludes If-Match and resolved today. Identical retries replay the same receipt and Location without a version bump, including across local midnight. A differing request with the same key returns `422 idempotency_key_reused`. Retrying the original key and body after undo returns the same receipt with undo metadata and does not change the item's version or re-complete it.
- Success is `201` with a durable receipt and no ETag; GET the item for its current ETag. A recurring item advances from the policy snapshot (fixed cadence or after-completion) and resets workflow state to open. A one-off becomes done while its receipt remains in history. Archived and done items cannot be completed; unarchive or enabling recurrence does not reopen a done item.
- GET `/completions` accepts `order=oldest|newest` (default `oldest`) and returns a live keyset walk by receipt ID; `newest` is descending UUIDv7 ID order (most recently recorded, not `completedOn`). Limit defaults to 50 and caps at 100. Oldest cursors are unpadded base64url `c1:<lowercase uuid>` and newest cursors are `c2:<lowercase uuid>`; malformed/unknown-version/cross-order cursors return 400 `invalid_query` parameter `cursor`. Checks run in this order: authentication; limit syntax/range and empty or repeated `cursor`; empty or repeated `order`; household membership; malformed item ID (404); unknown `order` value; cursor decoding; item existence. Membership and item existence are required even for empty history; archived/done items remain readable, and undone receipts stay in history.
- Undo the latest active receipt with `PATCH /completions/{completionId}`, `If-Match` and `{"undone":true}`. Every request requires exactly one syntactically valid strong ETag: missing returns 428; malformed, weak, wildcard, or list returns 412. Evaluation order is authentication, origin/authority, If-Match presence/syntax, body, membership and item/receipt existence, item row lock, then receipt lookup. Already-undone receipts replay unchanged after syntax validation; only the stored-version comparison is skipped, otherwise stale version returns 412. Archived returns 409, and a receipt other than the greatest-version active receipt returns `409 completion_not_latest`. Missing `undone`, null, wrong type, unknown fields, and malformed JSON return 400 `invalid_request`; `undone:false` returns 422 for field `undone` with `invalid_value`, before resource existence checks. Undo restores the receipt's attention anchor and prior workflow and clears one-off `done`, incrementing the item version. This restoration intentionally overwrites an `attentionOn` edit made after completion. Recurrence policy, title, notes, and subject are user choices and remain unchanged. Undoing successive latest receipts naturally restores prior cycles. The receipt is marked with `undoneAt` and `undoneByUserId`, never deleted. Completion POST idempotency replay after undo returns that original undone receipt and does not complete again.
- Item responses include read-only `done` and nullable `lastCompletedOn`; it is the completed date for the greatest `item_version_before` among non-undone receipts, or null if none. Item listing filters exact-match `done` (default false), independently of `archived`.

## Concurrency

- Single-resource `GET`, item/subject `POST` (create), and `PATCH` responses return a strong `ETag` such as `"3"`, the resource version. Completion `POST` returns a receipt without an ETag; fetch the item afterward for its current ETag. The version is not in the body.
- `PATCH` requires `If-Match` with one strong ETag. Missing returns `428`; anything not matching `^"[1-9][0-9]*"$`, or a stale version, returns `412`.
- Every successful update increments the version; an unchanged account role is a no-op with no version bump.
- Admin writes (invitation create, list and revoke, and role change) run in one transaction that locks the household row `FOR NO KEY UPDATE` gated by the caller's membership, then re-reads the caller's role. `FOR NO KEY UPDATE` avoids deadlock with the `KEY SHARE` locks taken by foreign keys referencing the household. Two admins demoting each other concurrently leave exactly one admin, and a demoted admin's in-flight admin write fails with `admin_required`.

## Regenerating and checking

- `make -C api generate` regenerates the TypeScript types (`api/generated/`) and the Go API models (`backend/internal/platform/httpx/apimodel/apimodel.gen.go`) using native Go and locked Node dependencies; it does not require Docker.
- `npm run check` in `api/` lints the contract, runs all three contract/health/OIDC checker test files, and fails if generated files differ from a fresh generation. Run `npm audit --audit-level=moderate` as part of verification.
- Migration 015 adds the attention-order index in a transaction. Creating it may briefly block writes to `items` while PostgreSQL builds the index. Migration 016 installs `unaccent` and `pg_trgm` in `public`, adds a derived search column populated by an update trigger, and builds a GIN trigram index; extension installation requires a migrator with trusted-extension install privileges. The backfill temporarily writes every item row and holds the migration lock.
- `bash scripts/setup-smoke.sh` records real responses and validates them against the contract.
