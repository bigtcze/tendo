# V2.1 maintainability audit

Status: all eight P1 hotspots, the ranked P2 items and the subsequent backend/script audit candidates listed in Refactor evidence are refactored and verified. At `efa6635` the frontend baseline is empty and `ci/maintainability-baseline.json` holds no production function-size, complexity or nesting exception; the remaining production entries are the two locale catalogue file-size entries (`frontend/src/i18n/cs.ts`, `en.ts`) and named long-line allowances, mostly SQL query files. Remaining function exceptions belong to test support and operational scripts. Snapshot and rankings are a measured triage of the current worktree; they identify review/refactor targets, not a mandate to split cohesive code solely to reduce line counts. Policy: `.autonomous/CODE_QUALITY.md` and `.autonomous/V2_1_SCOPE.md`.

## Inventory and measurement

- Production inventory excludes tests, generated code, immutable numbered SQL migrations under `backend/internal/platform/database/`, and test-only support. Test-support entries (including `itemtest`, `subjecttest`, `testpostgres/fixture.go`, `testoidc`, `backend/test/oidc-provider`, `frontend/src/test/`, and `frontend/e2e/` helpers) remain named where metrics trigger but are not ranked as production hotspots. `frontend/src/components/ui/` utility-class primitives and `HomeScreen` have separate design-system and frontend-home ownership rather than backend/test ownership.
- Other authored inventory includes frontend `src` TypeScript/TSX, API and scripts/deploy sources. Migration history remains immutable; generated sources remain subject to generation-drift checks.
- Go function measurements use `backend/tools/funcmetrics`: source lines, branch complexity, and maximum control-flow nesting. Function literals are measured separately with parent-qualified lexical names. ESLint measurements use the current pinned frontend dependencies and per-function-per-rule keys.

## Exceptions and ratchet

Named Go/file metric exceptions are in [`ci/maintainability-baseline.json`](../../ci/maintainability-baseline.json); frontend per-function-per-rule exceptions are in [`frontend/maintainability-baseline.json`](../../frontend/maintainability-baseline.json). Each entry records an allowed current value, technical rationale, and owning domain. Test-support entries document test doubles but are excluded from the production hotspot ranking.

The permanent CI/local ratchet checks tracked authored file size and long lines, Go function size/complexity/nesting, and frontend ESLint complexity/depth/function lines. New violations and worsened values fail; stale entries, missing targets, duplicate entries, and missing rationale/owner fail. Exceptions may only tighten or be removed. Generated sources, test suites, fixture data, and numbered embedded migration files (`backend/internal/platform/database/NNN_*.sql`) have explicit exclusions; none is a blanket application-code suppression.

Refactor evidence, before/after metrics, and relevant characterization tests should be added as each ranked target is addressed. This audit remains in progress until scoped high-risk hotspots are refactored and verified.

The checker also rejects exceptions whose allowed value is within the default threshold, so a baseline entry cannot be vacuous.
