# ADR 0014: Administrator-issued local password reset links

Status: accepted

## Context

Before 4.0 a household member who forgot the local password had no recovery path: an administrator could not set or hand out a password, and there was no email delivery to send a self-service link. V4 adds an administrator-issued reset link. The design, threat model and rejected alternatives are in section 3 of the [V4 baseline audit](../design/v4-baseline-audit.md#3-admin-password-reset-v4-08); this ADR records the decision only.

## Decision

- Identity owns the reset flow. `password_reset_tokens` stores `target_user_id`, `household_id`, the issuing administrator, timestamps and only the SHA-256 digest of the token; the token itself is 32 random bytes encoded as unpadded base64url and appears exactly once, in the `201` response. The web client builds `/reset-password#<token>`, so the secret never reaches a server, proxy or `Referer`, is never logged, and is never stored in cleartext. Rows are retained as audit history (issuer, creation, expiry, use, revocation).
- Lifetime is 24 hours, enforced by the service and independently by a database `CHECK` ceiling. The link is a bearer credential that replaces a password, so it must survive the administrator reaching the person through a private channel (a direct message, a phone call, a note handed over in person) but must not stay valid in an old conversation for days. A reset is therefore shorter-lived than an invitation, which only admits a member to a household.
- At most one link is outstanding per target: a partial unique index covers rows that are neither used nor revoked, and issuing again revokes the previous link inside the same transaction after locking the target and re-checking that it is still a member with a local password. An administrator cannot target themselves, because a stolen administrator session must not mint a new permanent credential, and an account without a local credential (OIDC-only) is refused.
- Redemption is public but requires the canonical `Origin` header, follows the same 15–128 character password policy as account creation, and hashes the new password before the transaction opens. Inside the transaction the token row is locked `FOR UPDATE` and re-authorized: the link must be unused, unrevoked and unexpired, the target must still be a member with a local credential, and the issuing administrator must still be an administrator of that household. Success marks the link used, replaces the hash, and deletes every session of the target. Every unusable state returns the same `404 invalid_password_reset`, so a link cannot be probed for whose account it belongs to or why it stopped working.
- Reset versus concurrent sign-in: `local_credentials.credential_version` increments on every password change. Sign-in verifies the password without a lock (Argon2 is slow), then opens one transaction, re-reads `password_hash` and `credential_version` with `FOR SHARE`, requires both to equal what it verified, inserts the session, and commits while still holding the lock. Redemption takes `FOR UPDATE` on the same row before writing the hash and deleting sessions. The two therefore serialize: either the sign-in commits first and its session is deleted by the reset, or the reset commits first and the sign-in fails exactly like a wrong password. An unlocked `INSERT … WHERE EXISTS (version = …)` is not sufficient under MVCC and is deliberately not used. The same lock-and-revalidate rule applies to every other password-authorized write, including the OIDC pending-continuation confirmation.
- Throttles are in-process, matching the rest of the authentication surface: issuance is limited per client address (10 per minute) and per target account (5 per hour), so one administrator cannot flood a person or use issuance as an account probe, and redemption is limited per client address (5 per minute) in addition to the password-work limit. All limits answer with the same `429 rate_limited` problem shape and `Retry-After`.
- The issue endpoint does not use `Idempotency-Key`. The web client's busy guard prevents a double submit, and a retry is harmless in the only way that matters: a second issue revokes the first link and returns a new one, so an uncopied link is replaced rather than duplicated, and a copied link keeps working until the person uses it or it expires.

## Consequences

- A backup contains the digests of outstanding links, so a restored copy accepts them again until they expire, exactly like pending invitations. Administrators who restore must treat that window as live credentials.
- Recovery for an OIDC-only account still depends on its provider; Tendo does not invent a password for it. There is no self-service "forgot password" form, no email delivery, and no global password reset.
- A successful reset signs the target out everywhere and the person must sign in again with the new password. Sessions created by the race described above cannot survive it.
- Every future password change must increment `credential_version` inside the same transaction, or sign-in revalidation stops protecting that path.
